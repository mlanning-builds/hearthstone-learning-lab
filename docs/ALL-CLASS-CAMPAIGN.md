## Parallel collection

The owner-authorized parallel continuation uses four CPU worker processes, each limited to one PyTorch thread. Workers collect a synchronous 64-game batch using identical frozen learner weights. The parent performs the unchanged PPO update only after all accepted results have been consumed in schedule order. No asynchronous policy lag, smaller model, shorter games, reduced epochs, fewer training samples, reduced evaluation budget or altered opponent proportions were introduced. The CPU trainer still uses two threads for its update. Evaluation remains serial.

Each attempt receives an independent policy RNG seed drawn from the saved master action RNG. First-attempt engine seeds are reserved before dispatch; retry seeds come after that reservation and keep the original slot's matchup, seats and frozen opponent. Completion order never selects the training sample set. An early safety stop discards the partial batch and all speculative later results; their reserved seeds stay consumed and any already-written diagnostics are speculative, not accepted training outcomes. The process pool closes before PPO starts. Infrastructure failures raise rather than becoming fake losses. Worker scheduling is reproducible by logical slot, but parallel trajectories are intentionally not bit-identical to the older single shared policy RNG stream.

The explicit migration accepts only the known pilot or prior all-class source fingerprints and the identical model/encoder/deck architecture. It preserves all model/optimizer tensors and RNG states, completed lessons, league and anchors, game position and cumulative training failure counts. Original checkpoints are immutable. Worker count is part of strict resume settings; future code changes still require review.

A non-training fixed-position benchmark measured observe/legal actions, encoding and frozen model forward passes. It made no policy action selections, completed no games and performed no optimizer steps. On this machine, 384 position passes took 17.85s with the original one-process/two-thread setup, 10.86s with two single-thread workers and 6.99s with four. This is 1.64x / 2.55x fixed-position throughput, not measured full-game collection speed. Checksums matched across configurations. Pool startup was roughly 3–4 seconds. Full-game variance, sample transfer, retries, memory pressure and concurrent workloads can reduce the gain.

Since historical batch collection and PPO each took roughly 210 seconds, a 2.55x collection improvement would project to roughly 5 minutes per batch instead of 7 minutes, before extra sample-transfer/straggler costs. With unchanged serial evaluations, roughly 18–21 hours is a planning estimate for the previous ~24-hour campaign, not a measured guarantee. Actual `collection_wall_seconds`, `collection_workers` and PPO timings are recorded per batch so the owner-started run can confirm or revise the estimate.


## Memory review — conservative two-worker default

Activity Monitor showed 13.85/16 GB memory used, 8.11 GB swap and a subsequent yellow pressure graph while the pilot and normal desktop apps were open. Swap totals include prior activity; the yellow graph is the more relevant current warning. A bounded single-process probe initialized the real collector's two frozen networks, registry and encoder from saved weights and forwarded 24 scripted lesson positions. It completed no games and ran no optimizer. Its process peak RSS was 331.09 MiB. This is a fixture measurement, not a full-game peak or proof of safe whole-batch memory use. Four simultaneous workers add roughly 1.3 GiB of that footprint alone, plus rollout/IPC buffers and the trainer's existing sample storage.

The configured default is therefore TWO workers, one CPU thread each. The four-worker benchmark above remains valid as an isolated throughput result, but its 18–21-hour projection is no longer the configured estimate. The two-worker probe achieved 1.64x collection throughput; roughly 20–22 hours instead of ~24 is a provisional overall estimate before full-game measurements. Close unused heavy apps before running; even two workers can cause pressure while this desktop remains crowded. No app was closed, no active pilot was stopped and no training was launched during this check. The current checkpoint migration preserves weights, optimizer, RNGs and completed lessons, changing the worker count only.
